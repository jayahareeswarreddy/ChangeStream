How ChangeStream works

ChangeStream demonstrates change data capture (CDC): make a normal PostgreSQL change and follow its event through Debezium and Kafka into a separate read model. The dashboard shows the live component health, events, and resulting data.

One database change, five stages

Each stage has a different responsibility. The dashboard’s green status means that service check is currently healthy.

1PostgreSQL sourceStores the original order. A committed change is written to the WAL.
2DebeziumKafka Connect’s PostgreSQL connector reads WAL changes with pgoutput.
3Kafka topicPersists events in cdc.public.orders for consumers.
4Python consumerReads events and applies them to the read model.
5Read model + APIA separate PostgreSQL database powers the dashboard and query endpoints.

Start the local demo

Docker Desktop must be running. Open PowerShell in the project folder, then start the stack and register the connector:

PowerShell · run from the project folder
if (!(Test-Path .env)) { Copy-Item .env.example .env }
docker compose up -d
python scripts/register_connector.py

Open the dashboard at http://localhost:8010. The connector takes an initial snapshot of three sample orders; those events show op: "r".

Make and follow a change

Run this from the project folder. The status and activity sections on the dashboard refresh every few seconds.

Insert an order
docker compose exec postgres psql -U postgres -d source_db -c "INSERT INTO orders (customer_name, status, total_cents) VALUES ('Demo', 'created', 2500);"
Update an order
docker compose exec postgres psql -U postgres -d source_db -c "UPDATE orders SET status = 'shipped', updated_at = NOW() WHERE id = 1;"
Delete an order
docker compose exec postgres psql -U postgres -d source_db -c "DELETE FROM orders WHERE id = 2;"

The order list shows the current read model; the event table shows the changes that arrived. You can also query the API at /docs.

Inspect Debezium and Kafka directly

The dashboard reports live health. These commands let you inspect the connector’s task and read serialized records from the Kafka topic itself.

Debezium connector status

Open the dashboard’s Inspect connector link or run:

Invoke-RestMethod http://localhost:8083/connectors/changestream-orders/status | ConvertTo-Json -Depth 5

Both connector and task should show RUNNING.

Watch new Kafka events

Start this in one PowerShell window. It waits up to a minute for a new event:

docker compose exec kafka /kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 --topic cdc.public.orders --partition 0 --offset latest --timeout-ms 60000

In another window, run one of the insert/update/delete commands above. Stop the listener with Ctrl+C.

Check all component health
Invoke-RestMethod http://localhost:8010/api/services | ConvertTo-Json -Depth 5
Why did I see old snapshot records? The Kafka command with --from-beginning starts at the oldest event in the topic. Snapshot events have op: "r"; new inserts, updates, and deletes use c, u, and d.

What happens to an event?

Debezium sends a change envelope with the row before and after the change, source metadata, and an operation code:

r · snapshotc · insertu · updated · delete
  1. Consumer reads the Kafka record. Its topic, partition, and offset identify this exact event.
  2. One read-model transaction applies the row and records the event. A unique topic/partition/offset key prevents duplicate application after a replay.
  3. Only after that database transaction succeeds does the consumer commit the Kafka offset. This is at-least-once delivery with replay protection, not a claim of distributed exactly-once processing.

Consumer lag is the difference between Kafka’s latest offset and the consumer group’s committed offset. If the consumer is stopped, new changes accumulate and lag rises; starting it again lets the read model catch up.

Scope and cleanup

This demo captures rows from one sample orders table. It does not currently accept arbitrary PDF/document uploads or answer questions over files; that is a separate RAG workflow. For document upload and grounded Q&A, see RAG Eval.

Stop services

docker compose down

Stops the containers and preserves the local database volumes.

Reset sample data

docker compose down -v
docker compose up -d
python scripts/register_connector.py

Deletes local Kafka/PostgreSQL state and re-seeds the sample rows.
